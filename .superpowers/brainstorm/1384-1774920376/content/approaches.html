3 approaches for editing transactions

The list + pagination + category filter are the same in all three — the difference is how edit/delete works

A

Extend AddTransactionScreen for edit

Tap a transaction → navigates to the existing Add Transaction screen, pre-filled with that transaction's data. A Delete button is added at the bottom. On save it calls PATCH instead of POST.

Pros

  • No duplicated form code
  • Familiar full-screen form UX

Cons

  • AddTransactionScreen gets more complex (create vs edit mode)
B

Bottom sheet modal on the list ⭐ Recommended

Tap a transaction → a modal slides up from the bottom with the edit form inline. Delete button inside the modal. User never leaves the list. Matches how BudgetScreen already handles editing.

Pros

  • Consistent with existing BudgetScreen pattern
  • User stays on the list, context preserved

Cons

  • Slightly more complex modal layout
C

Swipe to delete + tap to edit screen

Swipe a row left to reveal a Delete button. Tap the row to open a new EditTransactionScreen. Two separate interactions for edit vs delete.

Pros

  • Familiar mobile swipe pattern

Cons

  • Requires extra swipe gesture library or custom implementation
  • New duplicate screen for editing
